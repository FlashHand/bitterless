# FEATURE · 大文件的分片读取与位置标记（待实现）

> Ral 2026-09-11 提出，2026-09-12 记录待办：「当一个文件太大，例如占用空闲提示词的大部分的时候，
> 就可以触发压缩再去读，或者按用户意图分片去读一个文件，并总结（并标记位置，例如读了 1-1000 行、
> 1001-2000 行），免得上下文不够导致 agent 无法读大文件」

## 为什么需要

我们刚建了两条把内容推到磁盘、在提示词里只留**绝对路径**的机制：

| 机制 | 文件 | 谁会去读 |
|---|---|---|
| 超长粘贴转文件 | `<userData>/pastes/*.md` | 模型用 `read` |
| 每会话用户原话历史 | `<userData>/chain/<sessionId>.jsonl` | 模型用 `read` |

两条都把「读得动吗」这个问题**转移**给了 `read` 工具。一个 200 万字符的粘贴文件，
模型一次 `read` 就会把剩余窗口撑爆 —— 那时它既读不完，也没有上下文继续干活。
**所以这两条机制在大文件上是自我拆台的**，除非读取侧也有边界。

## 要解决的三件事

1. **触发判据** —— 「占用空闲提示词的大部分」要落成一个可算的数：
   剩余窗口 = 窗口 − 已用；文件估算 token = 字节/4。超过剩余的某个比例就不许整份读。
2. **分片 + 位置标记** —— 按用户意图分片读，每片带明确坐标（`1-1000 行`、`1001-2000 行`），
   模型据此知道自己读到哪、还差哪。**坐标必须在返回里**，不能靠模型自己数。
3. **分片后总结** —— 读完一片就压一次，只把摘要留在上下文，原文不留。
   否则分片只是把一次撑爆拆成十次撑爆。

## 尚未决定

- 分片是 `read` 工具自己做（对所有文件生效），还是只对这两个目录下的文件做？
- 「按用户意图分片」的意图从哪来 —— 模型自己给 offset/limit，还是宿主按关键词定位？
- 触发压缩再读：压的是**当前会话上下文**（腾地方），还是**文件内容**（边读边摘）？两者后果不同。

## 现状

**未实现。** 今天 `read` 是 pi 内置的，有 offset/limit 但没有自动分片、没有位置标记、
没有读后总结，也不看剩余窗口。
